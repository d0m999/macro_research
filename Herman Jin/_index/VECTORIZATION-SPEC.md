## 2. 三个必须先澄清的结构事实

这三条决定了切分方案。**都实测过，不要重新假设。**

### 2.1 `chapter` 是机械等分，不是语义分段

59 包**每包固定 6 章**，每章恰好占全片 **16.5–16.8%** 时长，字符数 1,550–1,667。

```
market-overview-2026-09-15：chapter-01 占 16.7% / 02 占 16.7% / … / 06 占 16.5%
```

⇒ **`chapter` 只能当"第几段"的定位编号，不能当语义块边界。**

### 2.2 真正的主题信息在 `manifest.chapters[].label`，而且会被机械边界劈开

`manifest.json` 的 `chapters` 数组（59/59 包齐全）含 `id / start / end / label`，其中 **`label` 是人工或模型判定的主题标签**：

```json
{"id":"chapter-01","start":0.0,"end":313.4,"label":"AI与科技产业"}
```

全库 28 种 label，前四类占 87.8%：

| label | 章数 | 占比 |
|---|---|---|
| AI与科技产业 | 97 | 27.3% |
| 宏观、利率与流动性 | 97 | 27.3% |
| 估值、盈利与市场定价 | 92 | 25.9% |
| 仓位、杠杆与资金流 | 26 | 7.3% |
| 风险情景与交易框架 | 18 | 5.1% |
| 其余 23 种（多为一次性细标签） | 23 | 6.8% |

**关键**：同一 label 在**相邻章重复出现**（2026-09-15 的 01 与 02 都是"AI与科技产业"；03 与 06 都是"宏观、利率与流动性"）。因为章边界是机械等分，**一个连续话题被切断成两章**。

⇒ 直接按 `chapter` 切 chunk = 把话题从中间劈开，两侧都不完整。
⇒ 正确做法：**先把相邻同 `label` 的章合并成一个"话题块"**。

合并后规模：

| 指标 | 值 |
|---|---|
| 每包话题块数 | 平均 **4.08**（分布：3–5 块占 46/59） |
| 全库话题块总数 | **241** |
| 单块中位时长 | 316 秒（≈5.3 分钟） |
| 单块中位字符 | ≈1,669 |

⇒ 合并后仍有 ~1,669 字符/块，**超出 800 token 上限，需块内二次切分**（见 §4.1）。

### 2.3 时间间隙不可用作切分边界

实测全库**真静音**（本段 `end` → 下段 `start`）> 5 秒的只有 **7 处**（59 包含计）。

⚠️ 易误判：段间 `start` 差值 >5 秒的有 936 处，但那是**段本身时长**（mean 2.1 秒），不是静音。用错了会把长段当段落边界。

⇒ **放弃"静音切段"路线**，只用 label 合并 + 长度窗口。

## 3. 缺口清单

### A · 切分单元不存在（最大缺口）

52,518 个视频段 p50 = 10 字符，1,619 段不足 4 字符。单段无检索价值（`CORPUS-INDEX-SPEC` §5.2 用邻接合并 ±N 绕开，但**向量库没有"合并"这一步**——embedding 是一次性的，必须在入库前完成聚合）。

### B · 必须新增 `embed_text` 派生字段，不能直接用 `text`

| 加工 | 为什么向量库需要而 FTS 不需要 |
|---|---|
| 繁→简归一化 | FTS 可用 query 扩展解决；但**繁简两种字形会产生两个方向的向量**，同一语义分裂到两个邻近区，top-k 被同义重复挤占 |
| 前置上下文头 | FTS 靠 `WHERE date/pkg` 过滤；向量库**只能靠文本内嵌**——孤立片段没有时空锚点，会被无关期次召回 |
| ASR 别名内联 | FTS 靠 `aliases` 表做 query 扩展；但"狗门"的音译形态**语义上与 Goldman 无关**，纯向量路线零召回。必须在**入库文本**里写成 `狗门(Goldman Sachs)` |

⚠️ `text`（原文）**永不修改**——`embed_text` 是独立列，删除可重算。

### C · 一手 / 二手必须物理隔离，且 `research/` 已混入非结论文档

- 若不隔离：RAG 会把研究报告的**结论**当成 Herman Jin 的**原话**引用（`CORPUS-INDEX-SPEC` §9.3 已立规，但那是"标注"，向量库里必须升格为**不同 collection**，因为相似度无法表达"这是二手的"）。
- **新增发现**：`research/` 现有 9 份文档中，**`audio-worklist-2026-09-20.md`（55,817 字符 / 233 节）是操作工单，不是研究结论**；`corpus-cleaning-review-2026-09-20.md`（10 节）是过程记录。若按"`research/*.md` = conclusion 层"整体入库，会把 **233 节工单**当结论检索出来。

⇒ 白名单入库，不用通配符。建议仅入：`herman-jin-2026-09-08-reading.md`、`herman-jin-core-reasoning-chain.md`、`herman-jin-core-views-price-validation-2025-2026.md`、`herman-jin-core-views-transcript-draft.md`、`herman-jin-data-sources-transcript-audit.md`、`herman-jin-main-views-since-2025.md`、`herman-jin-screen-2026-09-09.md`。

### D · 重复与噪声

| 项 | 量 | 处置 |
|---|---|---|
| X 回复正文重复 | **258** 条 | 内容哈希去重，保留最早一条，重复项记 `dup_of` |
| X 纯表情 | 447 条 | 不入库 |

## 4. 切分规范

统一参数：**目标 400 字符 / chunk，上限 800 字符，重叠 15%**（中文 400 字符 ≈ 250–400 token）。

### 4.1 视频（59 包 → 241 块 → ≈1.6k chunk）

```
1. 取 manifest.chapters[]，按 label 合并相邻同 label 的章 → 话题块（block_id = pkg + 序）
2. 块内按 transcript.jsonl 物理行号顺序取段，累积字符
3. 累积到 400 字符且下一段会造成跳跃 → 切；否则继续累积至 800 字符硬切
4. 相邻 chunk 重叠 15%（回退约 60 字符，即回退 5–6 段）
5. 记录 source_line_start / source_line_end（1-based 物理行号区间）
```

- **不跨块切**（块边界优先于长度上限）。
- **不跨包切**。
- 保留 `chapter` 字段（哪怕它是机械的）——它仍是稳定的定位编号，且用于生成"第 N 段"这类可读引用。

### 4.2 X（7,673 条 → ≈490 日块）

一条一 chunk **不成立**（主帖 p50 = 59 字符，回复 p50 = 18 字符）。改用**按日聚合**，实测恰好落在理想区间：

| 集合 | 活跃日 | 日均条数 | 日均字符 | p90 字符 | 处置 |
|---|---|---|---|---|---|
| 主帖 | 236 | 5.4 | **410** | 835 | 一日一 chunk |
| 回复 | 253 | 25.3 | **691** | 1,635 | 一日一 chunk；>800 字符的日按时间序二次切 |

- 日期用 `created_at` 转 UTC+8（`date_bj`），与 `CORPUS-INDEX-SPEC` §4.2 一致。
- 每个日块内**逐条保留 `post_id`**，chunk 元数据带 `member_ids` 数组，保证引用可回溯到单条。
- `in_reply_to_user` 为空的 477 条（1 月 438 条为主）→ 归入 `unattributed` 子块，标注"该月无回复对象信息"。

### 4.3 研究报告（7 份 → 316 节）

按**二级标题 `##` 切分**，一节一 chunk；超 800 字符的节按段落二次切。**必须**写入 `layer='conclusion'`，引用时强制标注"报告结论，非原话"。

### 4.4 幻灯片（814 张，可选）

不建文本集合。两个选项：

- **A（推荐）**：只把 `summary` 字段并入对应时间窗的视频 chunk 作为附属字段，不独立成 chunk。
- **B**：若需"看图找观点"，另建 image collection，用多模态 embedding；OCR 全文不入库。

## 5. `embed_text` 构造规范

```
embed_text =
    [ {date_bj} | {source_label} | {topic_label} | {chapter/日序} ]   ← 上下文头
  + "\n" + 归一化正文（zhconv → 简体）
  + ASR 别名内联（已确认别名表，见 CORPUS-INDEX-SPEC §10 附录 A）
```

实例：

```
[2026-09-15 | 市场概述 | AI与科技产业 | chapter-01]
今天讲一下 狗门(Goldman Sachs) 对 存储 板块的看法……
```

规则：

1. 上下文头**必须拼进 `embed_text`**，不能只放 metadata（embedding 看不到 metadata）。
2. 归一化用 `zhconv.convert(text,'zh-cn')`，与 FTS 侧**同一套**（避免两套索引字形不一致）。
3. 别名内联**只替换已确认的 25 条**（附录 A）。不做自动纠错——`CORPUS-INDEX-SPEC` §8.6 已警告别名表无法穷尽，宁缺勿错。
4. 别名替换是**衍生**行为：`text` 保持原文，便于比对与回听。
5. 剔除 `emoji-only`、`tier='noise'`。

## 6. Chunk 记录结构

```json
{
  "chunk_id": "mo-2026-09-15-b01-c002",
  "collection": "herman-jin-evidence",
  "embed_text": "[2026-09-15 | 市场概述 | AI与科技产业 | chapter-01]\n…",
  "text": "…原文，未改一字…",
  "metadata": {
    "origin": "yt-segment", "layer": "evidence",
    "pkg_id": "market-overview-2026-09-15",
    "date_bj": "2026-09-15", "month_bj": "2026-09",
    "topic_label": "AI与科技产业", "chapter": "chapter-01",
    "block_id": "b01",
    "source_path": "market-overview/market-overview-2026-09-15/transcript.jsonl",
    "source_line_start": 412, "source_line_end": 486,
    "start_sec": 148.2, "end_sec": 313.4,
    "char_len": 412,
    "member_ids": ["seg-000412", "…"],
    "source_hash": "sha256:…",
    "stale": false
  }
}
```

**硬性要求**：

1. `source_line_start/end` **必填**——已有 7 份报告用 `#L684-L715` 体例，chunk 必须能反向生成同样的锚点。
2. `member_ids` **必填**——X 日块要能回到单条帖。
3. `chunk_id` 稳定且可复现：`{pkg缩写}-{block序}-{块内序}`，**不含随机数**。
4. `source_hash` = chunk 覆盖区间的文本哈希。源文件变更时哈希不符 ⇒ 标 `stale=true`，**触发重建而非静默沿用**。

| 集合 | chunk 数 | 说明 |

## 8. 执行顺序（有严格先后）

```
[0] ~~等清洗收口~~ 已解除（§3-E：人工听音不做，清洗定格）

[4] 生成 embed_text（§5）                            ← 本文新增
```

## 10. 硬性规则

1. **原始文件只读**（沿用 `CORPUS-INDEX-SPEC` §9.1）。`embed_text` / chunk 全部是派生物，可删可重建。
2. **`text` 永不修改**。归一化、别名替换只作用于 `embed_text`。
3. **chunk 必须可回溯到行号**。失去行号 = 失去与已有 7 份报告的引用接口。
4. **一手与二手不同 collection**，不靠"标注"靠"隔离"。
5. **不按 `chapter` 直接切**（§2.1）。必须先合并同 label。
6. **不对噪声做"补救式入库"**。纯表情、OCR 碎片一律不入库。
7. **清洗未收口前不 embed**（§3-E）。文本一变，全部向量作废。

## 11. 对照路径：NotebookLM（能力边界已核实 2026-09-20）

**用途分工，不是二选一**：

| 用途 | 选择 |
|---|---|
| 人提问、快速探索、跨源对比、听播客 | NotebookLM |
| agent 调用、结构化查询、生成 `#L` 锚点引用、增量维护 | 自建（本文） |

**两者共用同一个上游**——规范化 Markdown。所以"要不要自建"不是现在必须定的事：先做上游导出，两边都能喂。

### 11.1 容量不构成阻碍（已核实）

- 单 source 上限 **500,000 词 / 200MB**，**所有档位相同**；无页数限制。
- sources/notebook：免费 50 · Plus 100 · Pro 300 · Ultra 500–600。
- 本语料总量 ≈117 万字符 ⇒ 远未触顶。

| 上传方案 | source 数 | 所需档位 |
|---|---|---|
| 甲：每包合并 1 个 md（60 + X 2 + research 7） | 69 | Plus |
| 乙：逐文件上传（60 transcript + 60 deck + 2 + 9） | 131 | Pro |
| 丙：视频按年合并 | ~13 | 免费 |
| **丁：实际采用（视频按月 + X 半年 + research 逐份）** | **32** | **免费** |

- **不支持 JSONL** ⇒ 必须先导出 Markdown/txt。
- 814 张 slide 图片若上传会 +814 sources，**必然超上限** ⇒ 只能选择性上传或转文本。

**丁 的产出**（`_index/derived/notebooklm/`，2026-09-21）：21 视频月包 + 4 X + 7 research = 32 件 / 1,187,997 字符。
粒度选**月**而不选**年**的理由是可**反选**：source 级复选框没有日期过滤，
切到月才能"手动关掉旧年份"——而时效性稀释对本语料是致命的（同一话题跨 20 个月反复讲）。

**一条例外规则（非《市场概述》系列的包）**：`market-overview-2026-05-14` 是 168X 频道
（@168X_Fortune）对 Herman Jin 的**专访**，不是其本人频道《市场概述》系列。
**用户 2026-09-21 决策：照常并入 `hj-video-2026-05.md`**（曾评估过单列，已回退）。
但该期**不使用 manifest 章节标签**——这类包的章节是**管线机械六等分**（每段恰为总时长 1/6），
不构成语义分段——改用**固定 15 分钟时间窗**分块，并在文件头与本期小节内声明。
脚本常量：`TIME_WINDOW_PKGS`。
**已知副作用**：该件 64,692 字符中 65.9%（42,632）是这场专访，与两期正常节目同权被检索；
若只想看《市场概述》，须在提问里限定日期。判定包是否属系列的字段是
`manifest.evidence_boundary` —— **加新包前先读它**。

### 11.2 七条不可绕过的差距

1. **无对外 API、无 MCP server**。仅 NotebookLM Enterprise（Gemini Enterprise / Discovery Engine）有 REST，且 source 须先托管到 GCS；消费档无程序化入口 ⇒ **agent 调不动**。
2. **引用锚点断裂**。NotebookLM 用自己的 passage 级引用，**不产生行号**；本仓库 7 份报告用 `#L684-L715`。用 `[L684]` 行号前缀伪装能否被它稳定引用 —— **未实测，不可假定可行**。
3. **只有 source 级 include/exclude 复选框**，没有元数据过滤 ⇒ §5 的日期/标的/期数过滤、`--stats`、`--export` 全部做不到。
4. **无分层与去噪控制**：工单类文档、OCR 碎片、258 条重复回复会与一手语料**同权**进入检索（见 §3-C/§3-D）。
5. **增量维护纯手工**：新一期要手工上传 + 重新索引；自建是全量重建 1–3 分钟（§7）。
6. **notebook 是孤岛**，官方无跨 notebook 检索。
7. **不能抓 source 内引用的 URL**，也不能补实时数据。

### 11.3 它确实更强的四点

1. **零开发成本，今天可用**；且检索上限**可能高于本项目自建的粗糙实现**——Gemini 长上下文 + rerank，对比本文方案的 400 字符 chunk + 小 embedding 模型。
2. 引用可点击回原文，人能直接核对。
3. Audio/Video Overview、Mind Map、Deep Research 是本文方案不具备的。
4. 官方声明不用于训练模型；语料本身是公开 YouTube / X 内容，**隐私不构成阻碍**。

### 11.4 建议顺序

1. 先做规范化 Markdown 导出（§5 的上游，**不含** chunk 切分）。**已完成**：`_index/derived/notebooklm/`，32 件。
2. **32 件一次全传**（清洗已于 2026-09-20 定格，§3-E，没有等待理由）。
3. 用**同一组问题**同时问 NotebookLM 与自建检索。**NotebookLM 答不出的问题，说明是语料问题而非索引问题** —— 可用它给 §9 验收清单定基准。
4. 只有在"agent 需要调用"或"需要结构化统计"这两条成立时，才继续建向量库。
