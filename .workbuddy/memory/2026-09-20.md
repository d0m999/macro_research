## 查明被清出的 gho_ token 是什么（17:35，结论）

- 用 token 自身的 API 响应头定性（不打印 token）：
  - `x-oauth-client-id: 01ab8ac9400c4e429b23`｜`x-oauth-scopes: read:user, repo, user:email, workflow`

- 类型 = **OAuth user-to-server token（`gho_`）**，非经典 PAT（`ghp_`）、非细粒度 PAT、非 App token。
- 签发应用 = **「GitHub for VSCode」**（VS Code 内置 github-authentication 扩展所用；Cursor/VSCodium/
  Windsurf 等 fork 复用同一 client_id）。**对照 gh CLI = `178c6fc778ccc68e1d6a`**，
  两者 client_id 不同 ⇒ **吊销它不影响 gh 登录**（更正此前「同属 GitHub CLI 应用」的误判）。

## 决策建议：自建 vs 三方（23:00，给用户的结论）

**倾向自建**，三条理由（均基于本次实测）：
1. **「别自建」的通常理由在此不成立**——自建的成本大头是文档解析（PDF 版面/表格/OCR），

   RAGFlow 那类产品最贵的能力在此用不上。
2. **行号锚点是硬接口**：7 份报告用 `#L684-L715` 引用，NotebookLM / ima / 秘塔只给 passage 级引用，
   自建天然带 `source_line_start/end`。**放弃自建 = 放弃已建成的引用体系**。
3. **规模小**：~2,400–2,500 chunk、约 100 万 token；全量重建 1–3 分钟、成本个位数人民币。
   落地方案：Ollama + Qwen3-Embedding（0.6B/8B，Apache 2.0，Apple Silicon 可跑）+ `sqlite-vec` 单文件，零运维。

**诚实保留的反面**：自建的检索质量**可能不如 NotebookLM**（Gemini + rerank vs 400 字符 chunk + 小 embedding）。
自建的优势不在「答得更好」，而在「agent 可调 / 有 #L 锚点 / 可按日期标的过滤 / 可重建」。
故沿用 §11.4：把 NotebookLM 当 baseline，同一组问题问两边。
