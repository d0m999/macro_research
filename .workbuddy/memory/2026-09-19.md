## 「每日复盘 skill」设计对齐（讨论轮，尚未落盘任何文件）

用户要做一个每日复盘 skill：他提供标的关注列表 → skill 去固定数据源抓数 → 按他写好的逻辑链推理 → 出当日复盘结论。

**本轮已达成一致的架构决策（后续实现必须遵守）：**

1. **五层结构**：L0 输入（关注列表 + 逻辑链）→ L1 抓数 → L2 判定 → L3 推理 → L4 产出。
   核心主张：**L2 判定层用确定性脚本，LLM 只在 L3 做串联与表述**。理由：LLM 自由裁量权重/方向会导致
   每日口径漂移、不可复现、事后无法校准。
2. **链结构采用「方案 C 混合」**：同主题的 A股/港美股标的共用一条共享链（标的挂节点）；
   加密资产（BTC/ETH）独立成链（驱动因子与股票链无因果连接，硬拼会造出假连接）；事件驱动个股单开短链。
3. **数据源分派：用户逐字段指定**。⚠️ 已知冲突待解：`westock-data` 与 `neodata-financial-search`
   两个 skill 各自都声明「命中能力域时禁止使用其它源」。规则必须是**按字段分派、一个字段只认一个源**，
   写死在映射表里，否则同一天两源给两个数字 → 复盘口径漂移。
4. **执行形态：按需手动，不挂 automation**。
5. **两处挂起**（用户明确说「先别急」）：加密数据源（BC/ETH 从哪里取）；字段级源分派明细。
   注意 westock 与 neodata **都不覆盖加密**，本仓库 `docs/` 下已有 Binance API / TradingView OI 对齐文档可复用。

**推进步骤（S0→S5）**：S0 定输入规格（产出 `chains.yaml` + `watchlist.yaml`）→ S1 数据源就绪检查
（产出字段级映射表，全缺则强制停车问用户）→ S2 最小闭环（1 条链 3 个标的，验收=用户读完能判断"今天要不要动"）
→ S3 快照 + diff（变更导向）→ S4 校准（首期必须诚实跳过，不许伪造方向）→ S5 挂定时（本用户跳过）。

**已识别的高危失效模式**（从 `believe-in-light` 引擎事故与项目历史教训迁移）：
- 双向信号符号反置（触发条件是「A 或 B」且两分支方向相反，配置只编码一个分支）→ 整条链方向翻向。
- 查不到时的"合理推测填充"→ 必须写「未查到」。
- 语料命中 ≠ 推荐（MU 反例：语料出现 4 期，本人明确说"我觉得美光很贵"）。
- 非交易日 / 财报未披露日生成伪复盘。
- 标的挂错节点（买的是"算力资本开支"，却挂在"存储涨价"节点上）→ 链错则后面全错。
