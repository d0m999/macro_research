## 关键经验（本轮实测）

1. **本机真正的瓶颈是内存闸门，不是磁盘。** 磁盘今日充裕（29→52 GiB，`DISK_GATE_GIB=25` 自然通过），
   但 `memory_pressure` 的 free percentage 长期钉在 **31–33%**，连续 25 分钟以上拿不到
   3 次 ≥35% 采样。物理 16 GiB、swap 已用 18.2 GiB，**无单一失控进程**，属累计负载
   （Chrome 1.18G + node 0.85G + codex 0.56G + Electron 0.53G + WorkBuddy Renderer 0.5G + Kimi 0.5G…）。
   → 续跑前**先量 `memory_pressure -Q`**，比量磁盘更能预判会不会卡。
2. **`wait_for_gate()` 不做 abort 判断**：跌破 `MEMORY_ABORT`/`DISK_ABORT` 只会无限 WAIT，
   abort 仅发生在 `run_logged()` 运行子进程期间。所以「WAIT + 资源很低」是设计如此。
3. **转录被 swapout 检查杀掉是常态，不是偶发。** 09-09 与 09-15 两期都在管线内转录跑了
   ~15–37 分钟后 `[requeue]`，进度全失（转录只在结束时写盘）。
   → **直接跑 `transcribe_worker.py` 应当作为默认路径**，而不是等失败后再绕。
   实测：1880s 音频 ≈ 15 分钟；2075s 音频 ≈ 17 分钟（单核 `nice -n 10`，无 `taskpolicy`）。
4. **改常量后必须重启 worker，而重启会丢掉抽帧阶段。** `collect_deck` 的选帧与 OCR 只存在于
   `/tmp` 临时目录，`write_standard_package()` 才复制进包。所以若在 deck/validation 阶段改阈值重启，
   要重付约 7 分钟的抽帧成本。**能改就该在下载阶段之前改。**
5. **`MEMORY_GATE` 是 `gate_ok()` 内部的统一启动阈值**（对所有阶段生效），
   `MEMORY_ABORT` 才是运行中硬保护。二者别混淆。
6. 昨日记录的绕行手段今天全部复现有效：`env -u` 清代理后 yt-dlp/HF 均正常；
   音频/转录产物齐全时管线自动走 `[resume]`，不重下不重转。
